# Architecture

Iter is a native macOS app (SwiftUI, Swift 6 language mode with complete concurrency checking), **deployment target macOS 26.0**: the lowest version that has the Foundation Models framework (`SystemLanguageModel`, `Tool`, `@Generable`) and `MKReverseGeocodingRequest`. Everything else used (WeatherKit `cloudCoverByAltitude` macOS 15, SwiftData, Swift Charts, MapKit for SwiftUI, Look Around) is older. No third-party code at build time or run time; XcodeGen generates `Iter.xcodeproj` from `project.yml`.

## Layout

```
project.yml              XcodeGen spec (Mac app target, hosted test target, signing, entitlements); includes project-ios.yml
project-ios.yml          the iPhone and iPad target (Iter iOS) and its test target, in the same Iter.xcodeproj
App/                     the Mac app's scenes, windows, commands and settings, plus the views, assets and string catalog both apps share
AppTests/                hosted tests: snapshot renderer (Design/snapshots) and live service checks
AppiOS/, AppiOSTests/    iPhone and iPad shell and screens, Info.plist; the iOS app tests
Packages/IterKit/        everything that is not UI: shared by both apps
Design/                  tokens.json (DTCG), TOKENS.md, SCREENS.md, COMPONENTS.md, snapshots/
Brand/                   Step (Geist 600) logo files and the First Light palette (Alpine kept in the palette files as history)
docs/                    this file, PERFORMANCE.md, ROADMAP.md, reference/ (the approved plan and flow briefs)
scripts/                 run.sh, test.sh, test-ios.sh, tokens.sh, make-icon.sh, snapshots.sh
```

## Platforms: what is shared and what is per platform

`project-ios.yml` is included from `project.yml` (`include: [project-ios.yml]`), so `xcodegen generate` writes one `Iter.xcodeproj` with both apps. The iOS target is `Iter iOS` (iPhone and iPad, iOS 26.0, bundle id `com.dwjames.iter.ios`, automatic signing with the same Personal Team) with the test target `IterAppTests iOS` (Swift Testing) and the scheme `Iter iOS`. `scripts/test-ios.sh` runs the package tests and the iOS tests on a Simulator.

| | Shared by both apps | Mac only | iOS only |
|---|---|---|---|
| Code | `Packages/IterKit` (every module); the views in `App/Sources` that compile on both | `App/Sources`: `Shell/IterApp`, `AppCommands`, `RootView`; the sidebar (`SidebarView`, `SidebarTripsSection`, `SidebarLocationsSection`; the context menus, badges and folder helpers in `Sidebar/` are shared); the AppKit-backed Explore (`ExploreView`, list panel, map pane), Locations (`LocationsView`, `LocationsMap`) and builder (`TripBuilderView`, `TripPlanList`, `TripRouteMap`); `ResizableSplit`; `Packages/IterUpdater` | `AppiOS/Sources/{Shell,Explore,Spot,Trips,Locations,Settings,Platform}` |
| Resources | The asset catalog (colours, app icon; iOS has an added 1024 pt icon) and the String Catalog | Mac entitlements and the updater public key in Info.plist | `AppiOS/Info.plist` |
| Version | `MARKETING_VERSION` and `CURRENT_PROJECT_VERSION` from `project.yml` | The updater and release scripts | Nothing: no updater yet (TestFlight or the App Store later) |

**The contributor rule.** A file added to `App/Sources` is compiled into both apps. If it needs AppKit, either exclude it in `project-ios.yml` (the Mac-only list) or guard it with `#if os(macOS)`. Shared views that differ in small ways use shims: `Components/PlatformStyles.swift` holds the link and checkbox style differences, and `AppiOS/Sources/Platform/PlatformBridge.swift` aliases `NSFont` to `UIFont` for shared text-measuring code and provides the `openIterSettings` environment action (iOS has no Settings scene).

**Navigation.** One `AppNavigation` (the same type on both platforms) is the source of truth: the selection (`SidebarItem`) and the paths of pushed spot routes. On iOS, `ShellState` maps the selection onto the iPhone tabs (Explore, Trips, Locations, Settings, and the search tab), and each phone stack is a computed binding over `AppNavigation`'s paths, so a shared view calling `navigation.show(.trip(id))` or `navigation.open(route)` works the same way on both platforms. The iPad uses `NavigationSplitView` with the sidebar Trips, Locations and Find and shows Settings as a sheet; at compact width it uses the phone shell.

**The Explore sheet is custom.** The iPhone Explore tab is a full-bleed map with a bottom sheet drawn inside the tab (detents peek, half and full). A system `presentationDetents` sheet was tried and covers the iOS 26 tab bar (verified on the Simulator), so the sheet is our own view.

**FoundationModels is weak-linked on iOS** (`-weak_framework FoundationModels`). Built with the iOS 27 SDK, the `@Generable` code referenced a symbol that iOS 26.5 does not have and the app stopped at launch. Ask checks availability before it uses the model.

**The first-run forecast source on iOS is OpenWeather.** WeatherKit needs a paid team, so the registered default for `iter.weather.primary` is OpenWeather. The key goes in Settings ▸ Weather (Keychain) or in a launch argument; see [TESTING-iOS.md](../TESTING-iOS.md).

## Data flow

```
 SwiftData store ──► IterStore (main actor) ──► view models ──► SwiftUI views
                                         ▲               │
 curated-spots.json ─────────────────────┘               ▼
                          AppEnvironment services (Sendable / actors)
                 ┌───────────────┬───────────────┬────────────────┬──────────────┐
          WeatherProviding   PlaceSearching   DriveTimeProviding   Scouting     Ephemeris
           (WeatherRouter,    (MKLocalSearch,   (MKDirections,      (Foundation   (IterAstro)
            see below)         MKGeocoding)      cache, throttle)    Models+tools)
                 └──────────────► LightEngine ◄─────────────────────────────────────┘
                                      │
                               DayLight / LightWindow ──► every light view draws the same window object
```

Weather in detail (`IterServices/Weather`; the facts and limits of each provider are in [DATA-PROVIDERS.md](DATA-PROVIDERS.md)):

```
 ForecastCenter ──► WeatherRouter (actor: primary, then the fallback)
                      ├─► AppleWeatherService ──► CachedWeatherService (actor)
                      ├─► OpenWeatherService ─┐   APIKeyResolver: environment ► launch argument ► Keychain
                      └─► WindyService ───────┤   CallBudget.reserve (UTC day, cap) ── before the network
                                              ▼
                              ProviderCache (per spot ~1 km, per hour)
                              OpenWeather: disk, through the next clock hour
                              Windy: memory only, 3 hours
```

`WeatherProviderFactory` builds the stack from `WeatherSettings` and re-points a running router when Settings change. A cache hit never reaches the budget. Every attempt is reported to an observer so Settings can show a status per provider. Each provider's mapping (`OpenWeatherMapping`, `WindyMapping`) is a pure function from response bytes to `Forecast`.

* **One window object.** `LightEngine.dayLight(...)` returns `DayLight` with five `LightWindow`s. The event unit, the timeline band, the arc marker, the hourly tint and the trip stop all read the same object, so they cannot disagree.
* **Honest unknowns.** A window gets a score whenever any forecast data has arrived. Hourly data scores the first 48 hours; daily summaries score days 3 to 8 at low confidence; beyond the provider's last forecast day the engine uses *persistence*: the last forecast day's weather carried forward by whole days, confidence forced to Low, with `ScoreNote.persistence` ("Beyond the forecast: the last forecast day's weather carried forward."). A window that began before the first forecast hour is scored from that first hour. `.noForecast(reason)` still exists in the model for a window with no data at all (never a number), but no screen draws it per row. A field a provider does not supply (OpenWeather has no cloud layers and caps visibility; Windy has no rain probability) is left unknown, never filled in; the score drops that factor, says so in a note (`ScoreNote`) and lowers confidence: the lead-time limits are 36 and 72 hours, 24 hours for the high level when any hour is interpolated from three-hourly steps, low for any daily-summary hour, and one step down for a window that needed cloud layers and had none. Outlook strips are clamped to the provider's horizon (`LightEngine.outlookDayCount`: 8 days with OpenWeather).
* **When there is no weather at all.** The only no-data situations (no key, offline, provider error) are one app-wide `WeatherStatus` (`ok`, `needsKey`, `offline(lastUpdate)`, `failed(reason, lastUpdate)`), kept by `ForecastCenter` and drawn once per screen as `WeatherStatusBanner` on Explore, Locations, the trip builder and the spot page ("Weather is offline. Scores are from the last update at 06:29."). `ForecastCenter` keeps the last good forecast per spot and coalesces what finishes: results arriving within a 40 ms window (an init parameter) apply together, and `revision` bumps once per batch and not at all for an unchanged result, so a fan-out re-runs the trip builder and Explore once. A forced request joins a fetch already running, and a provider that throws `CancellationError` on its own abandons the fetch so the place can be asked again. A failed refetch leaves the old score on screen; with none, the score slot is empty (a spinner while the fetch is in flight). `ForecastUnavailableReason` has an `offline` case, set from URLError connectivity codes. Settings and the banner text name the specific reason.
* **Weather for any location.** Every spot shown anywhere is fetched for its own coordinate on demand, through the shared per-spot-per-hour cache and the daily cap. Explore requests its rows in list order (a collapsed More Places when opened or as rows appear), Ask results and the Add Stop popover request what they list, and `AppModel.spotSaved` fetches a new or saved spot at once. A spot's default time zone comes from its coordinate (`TimeZoneEstimate` in IterData: the nearest curated spot within 150 km, else a whole-hour offset from longitude), never from the Mac; the reverse geocode replaces it with the real zone when it answers.
* **The headline rule.** A list row (Explore, Locations, Ask) shows the spot's *next sunrise or sunset event* in the spot's own local time (`LightEngine.nextEvent`): a window counts until it ends, after today's sunset the next is tomorrow's sunrise, it looks up to 4 days ahead, and the polar fallback is the first non-night window not yet over. Blue hours and night appear only in the Explore light panel and on the spot page. A trip stop shows its own session on its assigned day. There is no user intent setting: the "show light for" choice, the Explore date control and the spot page's intent picker are gone, and the spot page uses the spot's own best light. Rows, pins, the panel and trip stops draw the window as one event unit (`EventScore`): its symbol (`WindowSymbol`: `sunrise.fill`, `sunset.fill`, `moon.haze.fill` for both blue hours, `moon.stars.fill` for night), the score and the start time sit in one capsule filled with the band's ramp colour (one continuous fill, all three in the ramp text colour, the time lighter in weight), with the word as tooltip and VoiceOver label. `EventScore` replaced the earlier separate badge, chip and window line everywhere: Explore rows, map pins (Explore and Locations; the Locations pin takes its window from `AppModel.savedEvent(for:)`, the same call as the row), the light panel's header, the spot page, Locations rows, Ask rows, trip stops (the regular unit, alone: the unit is the whole rating and `ScoreLegend` explains the colours; band and confidence stay in its VoiceOver label), the trip overview strip (the compact unit) and the Add Stop popover. Pins are built with `EventScore(pin:zone:isSelected:)` from the cached `ExplorePinLight`, are borderless, and show selection by scale and shadow; the spot page's window rows name the window in words. Night is still its own window and cannot lift sunrise, sunset or blue hour.
* **Attribution per provider.** Each provider's required attribution (Apple Weather: Apple's mark and legal page; OpenWeather: "Weather data © OpenWeather", linked (ODbL); Windy: "Contains data from the Windy database", linked, and the Windy logo, not shipped yet) lives in Settings ▸ Weather ("Data Sources and Attribution") and Settings ▸ About (`WeatherDataSources`), at the owner's instruction of 2026-10-06 for this test build; the providers' terms ask for it where the data is shown, so this must be revisited before release (see DATA-PROVIDERS.md). Content screens name the source quietly: lists show one source line per distinct source (`ForecastSourceLines`), including a fallback ("OpenWeather (Apple Weather unavailable)"), and a single forecast shows its source line with the fetch time. The Settings change path: `WeatherSetup` re-points the router, then `AppModel` calls `ForecastCenter.invalidateAll()` so every screen refetches; ⌘R (`retryFailed`) re-requests only the failed forecasts.
* **The Windy map is a link, not a view.** Windy's widget terms exclude weather apps and commercial sites, and the Map Forecast API trial is development-only with keys bound to web domains. So the spot page (Windy section) and Explore (toolbar button) have "Open in Windy", which opens windy.com in the browser (`WindyLink`). Windy data is never stored on disk (its terms forbid it).
* **Grounded ask.** The model can only name places returned by its tools (MapKit search, curated spots). Its structured output refers to tool-result IDs; anything else is dropped before display. The Light Index, not the model, scores the window. Ask rows are built only from those grounded suggestions.

## Concurrency

* Swift 6 language mode, complete checking, no `@unchecked Sendable` except where a framework type forces it (documented at the site).
* View models and `IterStore` are `@MainActor`. SwiftData `ModelContext` is used only on the main actor; the store is small (hundreds of rows).
* Services are `Sendable` structs or actors. Weather and directions caches are actors keyed by rounded coordinate (provider caches also by UTC hour); directions requests are serialised with a minimum spacing to respect MapKit throttling, and a "no route" answer falls back to a labelled straight-line estimate and is final, while any other error (throttling, offline) stores nothing and is retried by the trip builder on a backoff timer (30 s, then 60, 120, 240, at most 300 s) while the builder is on screen, and by any refresh once the wait is over.
* Explore scoring runs off the main actor. `ExploreModel` keeps a score cache keyed by spot id, coordinate, zone, forecast state and five-minute time bucket; the derived rows only read it. A missing key is queued, and the row shows the spot's last computed event meanwhile, so a score never flashes empty. One coalescing scheduler waits about 40 ms after the first miss, takes the whole batch, runs `LightEngine.nextEvent` for all of it in one detached task (`LightEngine` is a `Sendable` struct), and applies the results in one observable change (`scoreRevision`, part of the derived stamp). Batches from an earlier time bucket are dropped. `waitForScoring()` is for tests.
* Explore map: `ExploreModel.mapItems` is the only thing the map pane draws. It is cached per derived stamp, visible region, selection, hover and pane size, ordered for drawing (dots, clusters, chips, the hovered pin, the selected pin last; by id within each), so the view does no sorting. A pin carries only what it draws (`ExplorePin`), so an unrelated forecast leaves every other annotation equal; rows and pins are `Equatable` and drawn with `.equatable()`, the list does not read the hovered id, and `EventScore` memoises the width of each event unit's text so a body pass does not measure it again. A finished Apple Maps search frames its results as a programmatic fit unless they are all already visible, so it works after the user has moved the map. `PinClusterer` groups pins into a grid fixed to world Mercator coordinates at a zoom bucket taken from the region's longitude span and the pane width (cells of about 48 pt), so panning never changes a cluster's id. The selected and hovered pins are never clustered; nothing is clustered before the first settle, with a zero-width pane, or below a 0.1° visible longitude span (`PinClusterer.minimumLongitudeSpan`), so co-located spots can always be reached. Clicking a cluster asks the camera policy for a fit of its members (a programmatic request, never a user move). Selecting a spot (row or pin) asks the policy for `selectionRegion`: a 25-mile radius around the spot (`MapCameraPolicy.selectionRadiusMiles`, a 50-mile span on the map's shorter side), or only a pan to centre it when the map is already closer in; it is a programmatic request too, and `closePanel()` asks for nothing. The base map is one shared setting, `MapStyleChoice` (key `iter.map.style`, Standard by default), read by every map through `@AppStorage`; each map has a `MapStyleMenu` button and the Mac View menu sets the same value. Nothing floats over the map: a selected place opens in the list column as the light panel (`ExploreLightPanel`), which replaces the list while `ExploreModel.showsPanel` is true. One selection drives pin, row and panel. A map selection opens the panel, a list click opens it after the double-click interval (the view calls `openPanel()`; arrow keys and Return open it at once), `closePanel()` goes back to the list with the selection kept, `selectNext()` and `selectPrevious()` step through list order, `panelPosition` gives "3 of 16", and clearing the selection, hiding the selected row, or any change to the query closes it. Because nothing covers the map, the reveal margins reserve no part of it. The panel draws the spot page's own sections at `SpotDensity.panel` (one `SpotModel` per place and day), so the page and the panel share their code.
* The trip builder has one `TripBuilderModel` per trip, kept for as long as the trip is open, so a redraw never builds a second model. It is organised by days: the overview strip of day cells, one box per day with a timeline (the Leave / Set up time column, `DriveRow` between stops, an Overnight line between days) and the route map's day switcher all read the same selected day. `TripBuilderModel` computes one `DayLight` per stop per refresh and reuses it while spot, day and forecast are unchanged (clock within 60 seconds); the scheduler takes those windows rather than solving them again. Legs the drive cache or an offline pack already knows are taken synchronously before the first recompute (`DriveTimeProviding.cachedLeg(from:to:)`, default nil), and legs arriving within 60 ms cause one recompute. The route map draws a precomputed `TripMapContent` (legs with paths, pins, day switcher) that changes only with the geometry. The `.iter` export is built on demand (`LazyTripDocument`), not in the body.
* Long work (forecast fan-out for many spots, Ask, pack downloads) runs in structured tasks owned by the view model and cancelled when the view goes away or the input changes. `SpotImageJobs` cancels an image job when the last view waiting for it leaves, and a later request replaces a cancelled job with a fresh one instead of joining it. Pack PNG encoding and writes run off the main actor (`@concurrent`).

## Persistence and sync readiness

SwiftData models follow CloudKit's rules so iCloud sync can be switched on later: every attribute has a default or is optional, no `@Attribute(.unique)`, every relationship is optional with an explicit inverse, enums stored as raw strings. Curated spots are not stored; a saved curated spot is a `PlaceRecord` with `curatedID` set.

**Schema versions.** `IterSchemaV1` (`SchemaV1.swift`) is the store as first shipped, frozen as nested copies of the three models. `IterSchemaV2` is the live models plus `FolderRecord`, and `TripRecord` and `PlaceRecord` gain `folder`, `sortOrder` and (trips) `isPinned` and `pinnedAt`. `IterMigrationPlan` has one lightweight stage, V1 to V2 (only optional relationships and defaulted attributes are added). `IterSchema.makeContainer(url:)` opens an on-disk store at a given URL for the migration test. Any later change to a model needs a new version.

### Editing saved places

`PlaceEdit` (IterData) is every field the place editor can change as one value; `IterStore.editPlace` applies it as ONE undo step (action `updatePlace`, shown as "Edit Location"), files the place in a locations folder, pins it, and skips an edit that changes nothing. No schema change was needed: `notes`, `tagsRaw`, `folder` and the pin fields already exist in V3, so there is no V4 (and the deprecated `FolderRecord.parent` stays: dropping it would need a migration for no user benefit). Ownership: a curated spot's coordinate, category, best light, walk-in and tags are the catalogue's, so `editPlace` leaves them alone and the editor shows them read-only with a footer; name, place, notes, folder and pin are stored on the saved record as the user's overrides. Re-saving or adding a curated spot to a trip refreshes only the catalogue facts (`PlaceRecord.applyCatalogue`), never those overrides. `IterStore.editableRecord(for:)` finds the record behind a spot (saved or own) and `current(_:)` gives the spot as edited, so cards and pages opened earlier update; Explore lists the edited copy of a saved curated or Apple Maps spot. `PlaceEditDraft` (IterFeatures) is the form state with validation; `AppModel.applyEdit` saves it and requests the forecast for a moved coordinate.

## Undo

Every structural or destructive edit (delete trip, delete spot, add, remove or move a stop, rename, change dates) goes through `IterStore`, which registers a named action on the window's `UndoManager` (Edit > Undo Delete Trip). Folder edits (create, rename, delete, move, pin) are undoable too: the store's undo state also holds folder snapshots, and every mutation touches each record whose fields it changes. The model context's own undo is not relied on, so action names are explicit and undo groups match user actions.

## Signing and capabilities

Bundle ID `com.dwjames.iter`, team `VF945J28YU` (a Personal Team, free provisioning), automatic signing with an "Apple Development" certificate. Hardened Runtime on; **App Sandbox off** for this direct-download build (see below). The WeatherKit entitlement lives in `App/Iter-WeatherKit.entitlements` and is used only when `scripts/run.sh --weatherkit` is run, because WeatherKit needs a paid Developer Program team with the capability on the App ID; see TESTING.md. API keys for OpenWeather and Windy live in the login Keychain (generic passwords, service `com.dwjames.iter.weather`, account = the provider's name). That is the file-based keychain, so it needs no keychain entitlement and does not use `kSecUseDataProtectionKeychain`. Keys are never in the repo, in UserDefaults or in logs.

**Why the sandbox is off.** Iter is distributed directly (GitHub Releases) and updates itself, and a sandboxed app can neither replace its own bundle nor clear the quarantine flag on what it downloads. So `App/Iter.entitlements` (and the WeatherKit variant) drop only `com.apple.security.app-sandbox`; Hardened Runtime stays on, and the other keys stay so an App Store build can restore the sandbox with one key. Such a build would have to drop IterUpdater and let the App Store update it (the updater refuses to install when `APP_SANDBOX_CONTAINER_ID` is set, and says why). Unsandboxed, SwiftData's default store would be `~/Library/Application Support/default.store`, a file every unsandboxed app shares, so the Mac app opens an explicit `~/Library/Application Support/Iter/Iter.store` (`StoreBootstrap`, `IterData.StoreLocation`). On the first unsandboxed launch it copies the old container's store, its `Iter/` folder (offline packs, forecast cache) and its preferences there, once, and leaves the container untouched as a backup. A `.migration-pending` marker in the store folder is written before the move and removed after the `Iter/` folder is merged, so a crash between the two is resumed on the next launch; files are copied through a temporary name so a crash never leaves a truncated file at its final name. Tests and in-memory runs never open an on-disk store.

## Map styles and the globe

Apple Maps' 3D globe is reachable only through the imagery styles. Probed in a standalone app (macOS 27 SDK) and on the iPhone Simulator (same MapKit): SwiftUI `Map` with `.standard(elevation: .realistic)`, with `emphasis: .muted`, with `pointsOfInterest: .excludingAll`, and plain `.standard`, camera distance 20,000, 30,000, 45,000 and 120,000 km, with and without `MapCameraBounds(maximumDistance: 200_000_000)`: always a flat Mercator world fit (the camera is clamped). `MKMapView` with `MKStandardMapConfiguration(elevationStyle: .realistic)` (default and muted emphasis), `cameraZoomRange` of 50,000 km and `greatestFiniteMagnitude`, and `setVisibleMapRect(.world)`: flat as well. `.hybrid(elevation: .realistic)` and `.imagery(elevation: .realistic)` (and the `MKHybridMapConfiguration` equivalent) at 20,000 km and beyond: the globe, with stars, atmosphere and city lights on the night side. The SDK has no public globe or projection setting; MapKit only carries a private flag (`ForceGlobeProjectionForStandardMap`), which Iter does not use. So `MapStyleChoice.default` is Hybrid, Standard stays selectable, and the `DaylightOverlay` day/night shade is drawn only for Standard (`DaylightClock.isShown`); imagery styles use MapKit's own night side. Maps pass `MapCameraBounds.globe` so the camera can reach the globe at all.

## Versions and updates

`MARKETING_VERSION` in `project.yml` (`settings.base`) is the one version number: semantic, `0.x.y` until the first signed release, which is `1.0.0`. The build number is the commit count on `main`, passed to `xcodebuild` by `scripts/version.sh` (0 when built from Xcode), and Debug builds also show the git short hash (`IterGitCommit`). Settings ▸ About, the About window and Settings ▸ Updates show them (`VersionText`).

`Packages/IterUpdater` is the in-house updater (Foundation, CryptoKit, Security; no third-party code). It reads `appcast.json` from the latest GitHub Release (`IterUpdateFeedURL`), picks the newest item for the channel and macOS version, downloads it with progress, checks length, SHA-256 and an Ed25519 signature against the public key embedded in Info.plist (`IterUpdatePublicKey`), unpacks it with `ditto` next to the app, checks that the bundle's identifier, version and build match the feed and that its code signature is valid, strips `com.apple.quarantine`, swaps the bundle with `FileManager.replaceItemAt`, and relaunches through a small shell that waits for the old process to exit. `UpdateController` (App/Sources/Updates) checks at launch at most once a day (Release builds; Debug defaults to off) and from **Iter ▸ Check for Updates…**, and drives the update window and Settings ▸ Updates. `scripts/release.sh` cuts releases and `scripts/updater-e2e.sh` checks the whole path with a fixture app on a local server. docs/DISTRIBUTION.md has the details, the signing keys and the first-release steps.

`Packages/IterKit/Sources/IterLicensing` holds licence keys (Foundation, Security, CryptoKit): the Lemon Squeezy client, the Keychain store with offline grace, `LicenseGate` and `LicenceSettingsModel`. It is built but off in 0.x; docs/LICENSING.md has the flow, the rules and the store setup.

## Testing and inspection

## Library and offline packs

**Folders.** `FolderRecord` holds a name, a kind (`trips` or `locations`; a folder never mixes kinds), a sort order and, in the store only for compatibility, a `parent` that is always nil. Folders are one level deep: nothing nests, because a photographer's library is a handful of trips or places per theme and a tree cost the UI (indents, disclosure, drop targets, back stacks) more than it gave. Stores written while nesting existed are flattened when `IterStore` opens (`flattenFolders`, idempotent): every nested folder becomes a top-level folder of its kind, placed right after its former parent in the list and renumbered 0, 1, 2..., keeping its name (same-name folders are never merged), pin, trips and places. `FolderRecord.parent` and `children` stay in schema V2 and V3 so no new schema version or migration stage is needed; only that migration reads them. Folders order by (sort order, name, id). Trips order within a folder, or unfiled, by (sort order, newest edit, id); a new or imported trip takes a sort order below the unfiled ones so it appears first, and a duplicate is filed right after its original. Places in a folder order by (sort order, name). Locations lists the saved and own places of a folder. Deleting a folder moves its trips to unfiled and its places out of any folder, and deletes only the folder; unsaving a place clears its folder. A pinned trip keeps its folder, but the sidebar shows it only in the pinned group (ordered by pin time), not in the folder. Every folder, move and pin edit goes through `IterStore` as one named undo action.

**Packs.** Pinning a trip (`PinnedTripDownloader.pin`) keeps it ready offline. For each pinned trip the downloader saves one pack to `Application Support/Iter/OfflinePacks/<trip UUID>.json`, with the images as PNGs in a folder of the same name beside it (`OfflinePackStore`). A pack holds the spots, the forecast for every stop coordinate (fetched through `ForecastCenter` and `WeatherRouter`, so the provider caches and the daily call cap apply), the real drive legs the scheduler needs with their route lines (never estimates), the place images (Look Around or satellite, requested at `layout/imageRequestWidth` by `size/imageStripHeight`, the strip's size) and a list of what failed. MapKit base map tiles are not included: MapKit has no public API to download tiles for offline use. A future option would need another map source or Apple adding one.

**State.** `OfflinePackStatus` is `none`, `downloading(done, total)`, `ready`, `stale(reason)` or `failed`, kept in memory per trip. A pack is stale when the trip changed after the download (`tripChanged`), when its oldest forecast is more than 12 hours old (`forecastOld`) or when something failed (`incomplete`). Download state is not in SwiftData: it is per device, and the pack on disk is the source of truth. `OfflineStatusBadge` draws it in the sidebar and the trip header.

**Lifecycle.** At launch `start()` loads the packs (seeding `ForecastCenter` with the last good forecasts, `OfflineDriveTimes` with the legs and the imagery cache with the PNGs, so a pinned trip opens complete with no network), cleans up (removes the packs of trips that are deleted or not pinned; unpinning alone leaves the pack until the next launch) and refreshes. It then refreshes every hour while the app runs. A refresh downloads again any pinned trip that is missing, stale or failed, or whose oldest forecast is more than 3 hours old; an item that fails keeps its previous data. In-memory and test runs use a throwaway folder (`IterApp`), so they never clean up the real packs, and tests do not call `start()`.

## Ask (the scout inside Explore search)

Ask replaced the Scout screen. The engine is unchanged in kind and now runs from Explore's search field (`ExploreModel+Ask`, over `ScoutModel`).

**Routing.** Return always runs the local search (`ExploreModel.submitSearch()` calls `searchAppleMaps()`; the curated filter applies as the text changes). `SearchIntent.classify` (pure, case- and diacritic-insensitive, whole-word) only decides whether an Ask row is also offered: `.ask` when the text has a question mark, starts with a request phrase ("show me", "where", "what", "which", "looking for", "somewhere", "best places", "spots" and similar) or a request verb from a fixed list ("find", "show", "take", "help", "give", "suggest", "recommend", "plan", "shoot", "photograph", "see", "watch", "catch", "explore", "visit", "hike", "go", "get", "want", "need", "chase"), or contains as whole words "near", "within", "for", "with", "sunrise", "sunset", "fog", "foggy", "misty", "forest", "coast", "hours", "drive", or a constraint marker ("hours of", "near me", "golden hour", "blue hour", "milky way" and similar); otherwise `.place`. Word count plays no part, so a long place name stays a place, and a name that carries a keyword ("Hoh Rain Forest") also gets the Ask row. There is one search field and no Ask toggle, mode or menu item (no ⌘4). `SearchSuggestions.make` (pure) turns the text into an Apple Maps suggestion ("Search Apple Maps for “text”", always first and the only one marked `isTop`) and, for `.ask` text, an Ask Iter suggestion ("Ask Iter: text") after it; an Ask that Apple Intelligence cannot run stays in the list as unavailable, with its reason. `ExploreModel.searchSuggestions` hides the Apple Maps row once its search is running or shown for that text, and the Ask row once an ask for that text is running or shown, so the Ask row stays beside the local results; `run(_:)` runs one and ignores an unavailable Ask. The view draws them at the top of the list (`ExploreSuggestionsView`): the Apple Maps row under an "Apple Maps" header with the return glyph, the Ask row with no header (its sparkle and "Ask Iter: text" title name it). Clearing the field resets the Ask.

**Area.** `ask()` passes the map's visible region to the scout (`Scouting.scout(_:near:progress:)`; a protocol extension keeps the two-argument form for fakes). With an area, the gathering prompt adds `The map shows the area around "the map". If the request names no place, use near: "the map".`, and `ScoutToolContext.centre(for:)` resolves "the map", "here", "this area" and similar to the area's centre (a place named "the map area") without geocoding.

**Pipeline.** Two sessions, because the on-device model's context is 4,096 tokens. (1) *Gather*: a session with tools (`FindPlacesTool` over MapKit, `CuratedSpotsTool`, `DriveTimeTool`) that registers every place it finds under a short ID. (2) *Pick*: a fresh session without tools that sees only the registered candidates and returns `@Generable ScoutAnswer` (IDs, a short reason limited to what the candidate data says, a window). `ScoutGrounding` drops any ID not in the registry and takes names and coordinates only from the registry. Parse failures are retried (greedy sampling) and tolerated when candidates already exist. Grounding is unchanged by the move into Explore.

**Results.** The results become an `ExploreSectionKind.ask` section, first in the list. Its rows are built only from the grounded `ScoutSuggestion`s, carry the scout's note (`ExploreRow.note`) and are scored by the same `nextEvent` path as every row. They ignore the text query and the filters, and their spot IDs are removed from the other sections. The map fits them too. Failures, including the unavailable states (device not eligible, Apple Intelligence off, model not ready), show in the section with "Search Apple Maps Instead".

## Search Here and Discovery

Search Here lists places in the part of the map you can see; Discovery looks beyond Apple Maps and the curated list. Both feed Explore's list and never move the camera (a typed feature search does fit its results). Source facts, endpoints, spacing and cache times are in [DATA-PROVIDERS.md](DATA-PROVIDERS.md#place-discovery-sources); this section is how the code is arranged.

**Search Here flow** (`ExploreModel+SearchHere`). `showsSearchHere` is true when the map has a region, the field is empty, nothing is running, and the list is empty or stale. `SearchHereRules.isStale` is the stale-region rule: the list's region is stale when the visible centre has moved by more than a fraction of the searched span, or the zoom has changed by more than a factor, so small nudges keep the list. `searchHere()` records the region, clears the earlier results and starts one task; a second press cancels it and bumps a generation counter, and every write checks `isCurrent(generation)` so a late child cannot land after a replacement or a Cancel.

1. *Apple Maps*, at once: scenic points of interest (`POICategoryMapping.scenicCategories`) and the natural-language queries "viewpoint", "lake" and "waterfall" run concurrently. Results are filtered for photo-worthiness (`SearchHereFilter`) and to the region, merged (`SearchHereMerge`) and shown straight away as the In View section. The status is `searchingMaps`.
2. *Ask and Discovery*, concurrently, when each is available (status `asking`). Ask (`Scouting.proposePlaces(in:areaName:context:)`, `RegionProposer`) only proposes names. Each name is then validated with an `MKLocalSearch` inside the region (`SearchHereValidator`); a name with no match inside the region is dropped, so no proposal becomes a row on the model's word alone. Discovery runs `Discovering.discover(area:feature: nil,…)` for the region.
3. *Merge*: after each source returns, all results are merged again (same place by id, or within 500 m with matching normalised names; sources unioned, Maps' category preferred, elevation kept) and published, so rows appear as sources finish. Rows that a curated or your own spot already lists are left out of the section (`inViewRows`, which scans only own spots near the results).
4. A failure is an outcome in `SearchHereStatus` (`maps`, `ask`, `discoveryOutcome`, per-source `discovery`), never a thrown error; only cancellation stops the lot. Typing in the field, another search or Cancel calls `cancelSearchHere()`, which cancels the task, bumps the generation and clears the section. Ask unavailable (no scout, Apple Intelligence off) leaves Maps and Discovery running.

**Discovery layer** (`IterServices/Discovery`, pure types in `IterCore/Discovery`). `DiscoveryProvider`s give places with names and usually coordinates and elevation: `OverpassProvider` (OpenStreetMap, using `FeatureKind.osmTags`), `WikipediaProvider` (geosearch plus intro extracts) and `WikivoyageProvider`. `DiscoveryTextSource`s give text, not places: `RedditSource` and `GoogleSearchSource` (only with the user's own key and engine id, from `DiscoveryKeyStore`, the Keychain). `FoundationModelsDiscoveryExtractor` copies place names out of that text with the on-device model; `DiscoveryExtractionFilter` drops any name that does not literally occur in the text, so the model never invents one and never supplies a coordinate. `DiscoveryValidator` gives every name-only place a coordinate by looking it up with Apple Maps, and keeps it only if the result lands inside the area and its name matches; places that came with a coordinate are kept only if the area contains it. `DiscoveryEngine` resolves an area (`resolveArea`, with a real OpenStreetMap boundary through `BoundaryResolving` when there is one), runs the enabled providers concurrently, validates, merges with `DiscoveryMerge` and ranks by `DiscoveryPreference` (popular, unique, mixed) up to `maxResults`; it returns a `DiscoveryReport` of places plus a status for each source (`ok(count)`, unavailable, needs a key). Explore depends only on the `Discovering` protocol, so tests put a scripted engine, or a real one over fixture providers, behind it. `DiscoveryHTTP` holds the shared HTTP behaviour: timeouts, the User-Agent, per-host spacing and a disk and memory cache; the limits are listed in DATA-PROVIDERS.md. A failing source never blocks the others.

**Feature-area queries** (`ExploreModel+Feature`, `FeatureAreaQuery`). `FeatureAreaQuery.parse` reads "<feature> in <area>" with one of a set of prepositions after a known `FeatureKind` (peaks, lakes, waterfalls, arches, viewpoints and so on, with synonyms). It rejects areas that are map phrases ("here", "me", "the map", "this area", "nearby", "around here") and strips trailing light or time words ("at sunset", "for sunrise", "at golden hour", "tonight", "this weekend") so "peaks in Glacier National Park at sunset" is the area "Glacier National Park". When an engine is present and a web source is on, the top search suggestion carries the parsed query and Return runs `runFeatureSearch`: the area is resolved (with its boundary polygon when OpenStreetMap has one), then Apple Maps searches the same text near the area while Discovery lists the feature, both inside the boundary (`DiscoveryArea.contains`; a place outside the outline is dropped, so "peaks in Glacier National Park" lists the peaks in the park, not those near its edge). Results merge into the Feature section, which the camera fits. If the area cannot be found the ordinary Apple Maps search runs and the status says so. All other text takes the ordinary Apple Maps path.

**Prompt prefix and taste summary.** `SearchSettingsModel` holds the choices (what the person likes to shoot, enabled sources, preference, result cap, learning from the library, whether a Google key exists) in `UserDefaults` under "IterSearch…" keys; the Google key and engine id live only in the Keychain. `TasteSummary.make(store:)` builds a short line from pinned and saved places and trips ("Recently saved: Mesa Arch, Tunnel View (desert, landscape); trips: Canyon Country"), capped in length, on the device. `discoverySettings(tasteSummary:)` produces the `DiscoverySettings` value, dropping the summary when learning is off. `DiscoveryPrompt` turns the prefix and summary into a bounded block that `AppleIntelligenceScout` adds to the Ask prompts through `ScoutContext`; they go to the on-device model only, never to Reddit, Wikipedia, OpenStreetMap or Google.

**Performance.** The In View, Feature and Ask rows are built inside `buildDerived`, which is cached by `DerivedStamp` (it carries `inViewRevision` and `featureRevision`, bumped when the result arrays change, so the stamp compares cheaply). `showsSearchHere` tests the stale region first and reads `rows` only when the list still matches. See [PERFORMANCE.md](PERFORMANCE.md).
